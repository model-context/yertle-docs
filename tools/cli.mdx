The Yertle CLI is an open-source Python command-line client for exploring and scripting Yertle workspaces.

**Repo:** [model-context/yertle-python](https://github.com/model-context/yertle-python) · **Package:** [`yertle` on PyPI](https://pypi.org/project/yertle/)

## Installation

The CLI ships in the `yertle` package on PyPI. Install it as a tool with
[`uv`](https://docs.astral.sh/uv/):

```bash
uv tool install "yertle[sre]"
```

That gives you `yertle` and `yertle-sre`. `pipx` works the same way.

The MCP server is deliberately not part of a tool install — MCP hosts launch
it themselves via `uvx`, so it never needs to sit on your PATH. See
[Yertle MCP Server](/tools/mcp) for the client config.

Verify:

```bash
yertle version
```

<Note>
  Every command lands on your PATH whichever extras you pick — Python entry
  points are not conditional on extras. So `yertle[sre]` still creates a
  `yertle-mcp` you will not use. Running it tells you which extra it needs
  rather than failing obscurely. Install the extras you want to **use**, not
  the ones you want to see.
</Note>

To upgrade later:

```bash
uv tool upgrade yertle
```

That works as long as you installed without pinning a version. Pinning
(`uv tool install "yertle[sre]==0.3.0"`) records the exact version as the
requirement, so later upgrades have nothing to move to — reinstall with
`uv tool install --force "yertle[sre]"` to unpin.

## Getting started

```bash
# Save a personal access token to ~/.yertle/config.json
yertle login

# Confirm which backend and token are in effect
yertle auth status

# Get oriented
yertle about
```

`yertle login` defaults to production. Pass `--api-url` to point at a different
backend and persist that choice, or set `$YERTLE_API_URL` for a single command.

## Commands

Commands are noun-then-verb, like `gh` and the AWS CLI. A bare noun prints its
subcommands rather than running a default action.

### Organizations

```bash
yertle orgs list              # organizations you belong to
yertle orgs show <org-id>     # one organization in detail
yertle orgs use <org-id>      # set a default org — or `all` to undo
```

### Nodes

```bash
yertle nodes list             # every node, with relationship counts
yertle nodes tree             # the containment hierarchy
yertle nodes show <node-id>   # tags, parents, children, connections
yertle nodes search "<query>" # rank nodes by meaning, not by name
```

`nodes search` is the fastest way from a description to a node. Add
`--expand standard` to pull in the surrounding nodes and connections in the
same call:

```bash
yertle nodes search "how do users reach the app" --expand standard
```

It also takes `--top-k`, `--tag key=value` (repeatable), `--scope-root`,
`--dir-prefix`, and `--include-text`.

### Authentication and diagnostics

```bash
yertle auth status            # effective API URL, token, and org
yertle version                # installed version
yertle about                  # data model and common workflows
```

`yertle auth status` is the first thing to run when something behaves
unexpectedly. It reports what is in effect alongside the source each value was
resolved from, without making a request:

```
  API URL  https://api.yertle.com                (from $YERTLE_API_URL)
  Token    yrt_a1b2…f9e0                         (from ~/.yertle/config.json)
  Org      2c440b7a-d5bd-4f0d-9264-8da3195497af  (from ~/.yertle/config.json)
```

It exits non-zero when no token resolves, so it works as a precondition check
in scripts.

## Choosing an organization

Most commands act on one organization, resolved in this order:

| Priority | Source |
|---|---|
| 1 | `--org <id>` flag |
| 2 | `$YERTLE_ORG` |
| 3 | `yertle orgs use <id>` (saved in `~/.yertle/config.json`) |
| 4 | Every organization you belong to |

```bash
yertle orgs use 2c440b7a-d5bd-4f0d-9264-8da3195497af
yertle nodes list    # no --org needed from here on
```

Commands that can span organizations — `nodes list` and `nodes tree` — do so by
default. Commands that cannot address more than one — `nodes show` and
`nodes search` — ask you to pick one.

## Output formats

Every data command takes `--format table` (default) or `--format json`. Errors
go to stderr and exit non-zero, so piping is safe:

```bash
yertle nodes search "payment path" --format json | jq '.matches[].title'
```

## Configuration

Credentials resolve per key, so the two settings can come from different
places:

| Setting | Resolution order |
|---|---|
| Token | `$YERTLE_TOKEN` → `~/.yertle/config.json` → error |
| API URL | `$YERTLE_API_URL` → `~/.yertle/config.json` → `https://api.yertle.com` |

```bash
export YERTLE_TOKEN="yrt_..."
export YERTLE_API_URL="https://api.yertle.com"
```

Environment variables take precedence over the config file, which makes them
the right way to point at a different backend for a single command without
disturbing saved credentials. `yertle login` writes the config file with
owner-only permissions (`0600`) and merges into any existing contents rather
than replacing them.

<Note>
  **Upgrading from 0.2.0 or earlier:** `yertle orgs` is now `yertle orgs list`.
  Every command is noun-then-verb, so a bare `yertle orgs` prints its
  subcommands instead of listing. `yertle login` no longer requires
  `--api-url`; it defaults to production.
</Note>
